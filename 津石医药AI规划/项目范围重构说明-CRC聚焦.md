# 津石医药 CRC 访视风险助手 — 项目范围重构说明

> 重构日期：2026-07-30  
> 重构目标：剔除“医生/医院系统”场景，聚焦“CRC（临床研究协调员）”独立工具侧，降低系统接入成本，提升落地可行性。

---

## 一、重构背景与产品判断

### 1.1 为什么从“医生/医院系统”回退到“CRC”？

原规划将 AI 辅助能力同时覆盖 CRC 与医生/研究者，并希望通过医院内网对接 HIS/EMR 获取检测数据、辅助临床决策。但在落地评估中发现：

- **医院系统接口封闭**：HIS/EMR/电子病历系统的接口开放度低，数据脱敏、合规审批和 IT 对接周期长。
- **商务周期不可控**：医院信息科、科室、伦理、申办方多方审批，MVP 阶段难以在多个中心快速复制。
- **医生决策场景风险高**：任何涉及临床诊断、用药方案、最终安全判定的 AI 输出，都面临极高的医学责任和监管不确定性。
- **CRC 是可控入口**：CRC 是津石内部角色，对工具形态、数据采集方式、反馈闭环有直接控制权，可通过“手动上传/Excel 导入 + 本地 Web 工具”快速启动。

因此，本轮重构将产品边界严格收缩为 **CRC 独立工具**：CRC 将检测报告上传/导入平台，平台后端接入 CTCAE 和医学专业知识知识库，对检测结果进行预识别标注并返回给 CRC；CRC 依据 AI 预识别标注对线下检测报告表进行标注，在线下获取医生确认后，将 AI 预判正确的内容用于病例填写。

### 1.2 产品改进的核心逻辑

| 维度 | 重构前 | 重构后 | 产品意义 |
|------|--------|--------|----------|
| 目标用户 | CRC + 医生/研究者 + PM + 质控 + 客户 | CRC + CRC 组长 | 聚焦高频痛点用户，减少多角色协同的复杂度 |
| 数据来源 | 医院 HIS/EMR/电子病历对接 | CRC 手动上传 / Excel 导入 | 零医院系统接入成本，可在任意中心快速试点 |
| 核心价值 | 临床决策支持 + 流程优化 | CRC 行政/数据效率提升 | 把 AI 从“决策支持”拉回“事务性辅助”，风险可控 |
| 落地可行性 | 低（受医院系统制约） | 高（CRC 自主操作） | MVP 可在 1-2 个中心快速验证并复制 |

## 二、逐文件修改说明

### 2.1 AI 场景优先级矩阵（V1 + V2）

**修改文件：**
- `津石医药-访视风险预测与智能提醒AI场景优先级矩阵.yaml`
- `津石医药-访视风险预测与智能提醒AI场景优先级矩阵.html`
- `津石医药-访视风险预测与智能提醒AI场景优先级矩阵-V2.yaml`
- `津石医药-访视风险预测与智能提醒AI场景优先级矩阵-V2.html`

**主要修改：**

1. **删除非 CRC 核心场景**（共 6 个）：
   - 多角色协同任务编排引擎
   - 风险闭环与 CAPA 自动跟踪
   - 客户视角风险摘要自动生成
   - 中心/CRC 风险画像与运营复盘
   - 访视风险周报自动摘要
   - 跨项目风险规则迁移模拟器

2. **重命名“医生复核材料自动整理”为“EDC 录入辅助与复核证据包整理”**，明确其定位为 CRC 将检测报告导入后，AI 输出预识别标注和复核证据包，辅助 EDC 字段回填。

3. **引入“落地可行性”评分维度，权重从 40% 提升至 70%**，技术复杂度权重降至 30%。新公式：

   ```
   Priority = (User × Frequency × Value) / [Feasibility × 0.7 + (Data + AI + Knowledge)/3 × 0.3]
   ```

   其中 Feasibility 主要映射“集成复杂度”，重点压低需医院 HIS/EMR 对接的场景。

4. **重新计算所有场景优先级分数并排序**，确保高价值机会落在 CRC 独立工具侧。

**产品改进价值：**
- 优先级排序与落地约束对齐，避免资源投入在商务周期不可控的医院系统对接上。
- 明确 MVP 主线：CRC 下一步动作智能提醒 → 受试者状态异常预判 → EDC 录入辅助与复核证据包整理 → AE/SAE/CM 升级判断与 SLA 倒计时。

   - 低价值·易落地：CRC 事务性工作

   > “高价值机会全部落在无需医院 HIS/EMR 对接的 CRC 独立工具侧；任何需医生决策或医院系统集成的方向因商务周期长、接口封闭，本轮暂缓。”

**产品改进价值：**
- 用象限图可视化地约束产品边界，让团队、客户和投资人一眼看到：本轮不做医院系统对接，所有高价值机会都围绕 CRC 独立工具展开。

### 2.4 本体设计（Ontology）

**修改文件：**
- `津石医药-CRC访视风险智能助手本体设计.yaml`
- `津石医药-CRC访视风险智能助手本体设计.html`

**主要修改：**

1. **新增 5 个 CRC 专属实体：**
   - `Site`（研究中心）：CRC 管辖范围与资料收集的现场单元。
   - `Patient`（受试者）：参加临床试验的受试者主体。
   - `Visit`（访视窗）：项目方案定义的访视时间窗和检查要求。
   - `Query`（质疑单）：数据管理员或质控对 EDC/资料的质疑。
   - `SDV`（源数据核查）：EDC 录入数据与源文件一致性的核查记录。

2. **删除与“诊断、用药方案”相关的实体/关系描述：**
   - 将 `source_document` 描述中的“病历、用药记录”改为“化验单、影像、检测记录和访视记录”。
   - 将 `sop_rule` 的 `clinical_review` 规则类型改为 `review_trigger`。
   - 将 `action_recommendation` 的 `contact_doctor` 动作类型改为 `发起复核`。
   - 删除或改写所有“医生复核”“临床诊断”“用药变化”等描述。

3. **关系精简为仅保留三类：管理、触发、记录。**
   - 删除原有关系：属于、包含、依赖、生成、产生、校准。
   - 新增 Site→Visit Task、Patient→Subject Visit、Visit→Subject Visit、Source Document→SDV→Query→Action Recommendation 等 CRC 工作流关系。

4. **修改动作边界（Action Boundaries）**：将“输出临床诊断结论”“直接判定受试者是否安全”等禁止动作改为“输出最终临床判定结论”“AI 只能辅助判断，不能替代临床判定”。

**产品改进价值：**
- 本体层明确区分“CRC 行政/数据事务”与“医生临床决策”，从知识建模层面防止 AI 越界。
- 新增 Site/Patient/Visit/Query/SDV 五个 CRC 高频操作对象，使 Agent 的上下文理解、动作推荐和反馈闭环更贴合 CRC 实际工作。

## 三、产品改进总结

### 3.1 从“决策支持”到“事务性效率工具”

重构前，产品价值主张偏向“临床决策支持”和“多角色协同优化”，落地路径依赖医院系统。重构后，产品价值主张明确为：

> **提升 CRC 行政与数据效率**：通过 AI 预识别标注、复核证据包整理、下一步动作提醒和 EDC 录入辅助，减少 CRC 在检测报告判读、资料整理、字段回填和状态同步上的重复劳动。

### 3.2 从“系统对接”到“人工导入”

数据来源从医院 HIS/EMR 对接回退到 CRC 手动上传/Excel 导入。这不是技术倒退，而是**产品策略的主动选择**：

- 用人工导入绕过医院系统接口封闭的瓶颈。
- 用 OCR/文档解析 + CTCAE 规则引擎 + 医学知识库，在导入瞬间完成高价值预识别。
- 保留线下医生确认环节，确保医学责任和合规边界清晰。

### 3.3 从“多角色协同”到“CRC 单点闭环”

本轮 MVP 不再向医生、PM、质控、客户直接推出协同产品，而是：

- 只服务 CRC 的一线操作。
- 将其他角色的责任边界、升级规则和处置模板沉淀为知识库，供 CRC 查询和引用。
- 后续二期再考虑基于 CRC 数据沉淀，扩展 PM/质控视角的闭环管理。

### 3.4 风险与收益再平衡

| 风险点 | 重构前 | 重构后 |
|--------|--------|--------|
| 医院系统接口不可获得 | 高 |  eliminated（人工导入） |
| 医生决策责任边界 | 高 | 清晰（AI 只辅助，医生线下确认） |
| 多中心复制速度 | 慢 | 快（无需医院 IT 审批） |
| 一线采纳率 | 不确定 | 更高（直接解决 CRC 日常重复劳动） |
| MVP 交付周期 | 长 | 短 |

## 四、后续建议

1. **试点选择**：优先选择 1-2 个研究中心的 CRC 进行本地 Web 工具试点，验证 OCR 识别准确率、CTCAE 规则命中率和 CRC 采纳率。
2. **数据回流**：将 CRC 的采纳/修正/误报/漏报反馈作为规则优化和模型迭代的真值来源，但需 CRC 组长或质控复核后方可进入训练。
3. **二期扩展**：在 CRC 闭环数据稳定后，再评估是否需要向 PM/质控输出风险看板，或与客户协同门户对接。
4. **合规护栏**：持续强化“AI 不输出临床判定、不替代医生最终确认”的边界，所有输出必须附带置信度、规则依据和人工确认入口。
